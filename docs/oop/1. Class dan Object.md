# Modul 1. Class dan Object

[Kembali ke indeks OOP](README.md). Diselaraskan dengan source project utama, 23 Oktober 2026.

Dua pelanggan dapat memakai rancangan keranjang yang sama, tetapi isinya berbeda. Dari contoh itu kita membedakan class sebagai definisi perilaku, object sebagai instans yang dipakai program, dan state sebagai nilai yang melekat pada instans tersebut. OOP mulai berguna ketika data dan pekerjaan atas data itu dapat ditelusuri bersama.

## Tujuan pembelajaran

- Membedakan class, instans, referensi, dan state menggunakan kode proyek.
- Menjelaskan peran constructor dan self tanpa menyamakan object dengan satu baris database.
- Menelusuri lima object dengan tanggung jawab berbeda.

## Bekal istilah

| Istilah | Makna saat membaca kode |
|---|---|
| Class | Definisi atribut dan perilaku; bukan data satu pelanggan. |
| Object/instans | Hasil instansiasi class yang memiliki identitas dan keadaan sendiri. |
| self | Parameter yang menunjuk instans penerima pemanggilan method. |
| `__init__` | Menginisialisasi instans; penyimpanan database adalah langkah terpisah. |

## Kasus 1. Dua menu memakai rancangan MenuItem yang sama

**Berkas utama:** [menu/models.py](../../menu/models.py#L68). **Simbol yang dibedah:** `MenuItem`.

### Masalah yang dihadapi

Staf mencatat dua menu dengan nama dan harga berbeda. Kita membutuhkan satu rancangan data yang konsisten agar kedua menu dapat ditampilkan, dicari, dan dipakai pada transaksi. MenuItem menyediakan rancangan itu lewat field Django serta perilaku seperti `__str__` dan save.

### Cuplikan kode nyata

Cuplikan `MenuItem.__str__` dari berkas sumber. Import dan bagian lain tidak ditampilkan.

```python
def __str__(self) -> str:
    return self.name
```

### Bedah alur dan tanggung jawab

1. Baca deklarasi MenuItem(models.Model), lalu identifikasi name, price, category, dan is_available.
2. Bandingkan field pada class dengan nilai yang akan dimiliki setiap instans; keduanya berada pada tingkat yang berbeda.
3. Telusuri `__str__`: saat suatu instans diubah menjadi teks, method membaca self.name milik instans tersebut.
4. Baca save untuk melihat pemrosesan foto dan penerusan penyimpanan ke induk Django.

### Contoh input dan hasil yang perlu dijelaskan

Sebagai ilustrasi, MenuItem(name="Nasi", price=Decimal("18000")) dan MenuItem(name="Teh", price=Decimal("5000")) menghasilkan dua instans di memori. Mengubah nama instans pertama tidak mengganti nama instans kedua. Instans itu belum merupakan menu tersimpan yang lengkap: category wajib diisi dan penyimpanan dilakukan melalui alur model/form.

### Hubungan dengan konsep OOP

Class menyatukan struktur dan perilaku yang dapat dipakai berulang. self membuat satu method bekerja pada data object penerima, bukan pada semua menu sekaligus. Django menambahkan mekanisme ORM; kemampuan itu berasal dari framework, sedangkan field dan override di file ini merupakan konfigurasi/perluasan proyek.

### Batas penerapan dan kekeliruan yang perlu dihindari

Memanggil constructor tidak sama dengan INSERT. Memanggil save juga tidak otomatis memanggil full_clean pada semua model. Untuk latihan tanpa database, cukup jelaskan instans di memori; jangan menganggap data contoh telah tersimpan atau semua constraint telah diperiksa.

### Latihan penelusuran

Tentukan class, dua instans, dua state berbeda, dan satu perilaku yang sama. Kapan query database baru diperlukan?

## Kasus 2. Budget tiap pelanggan menjadi object nilai tersendiri

**Berkas utama:** [recommendation/services/budget.py](../../recommendation/services/budget.py#L53). **Simbol yang dibedah:** `BudgetConstraint`.

### Masalah yang dihadapi

Pelanggan A mencari makanan maksimal Rp10.000 dan pelanggan B maksimal Rp20.000. Satu variabel global akan membuat batas mereka mudah tercampur. BudgetConstraint mengemas batas masing-masing sebagai object dengan aturan pembentukan yang sama.

### Cuplikan kode nyata

Cuplikan `BudgetConstraint.allows` dari berkas sumber. Import dan bagian lain tidak ditampilkan.

```python
def allows(self, price: Decimal) -> bool:
    if self.minimum is not None and (
        price < self.minimum or (price == self.minimum and not self.minimum_inclusive)
    ):
        return False

    if self.maximum is not None and (
        price > self.maximum or (price == self.maximum and not self.maximum_inclusive)
    ):
        return False

    return True
```

### Bedah alur dan tanggung jawab

1. Baca parameter minimum dan maximum pada `__init__`; keduanya dapat bernilai None.
2. Ikuti validasi nilai finite, nonnegatif, batas nominal, dan minimum yang tidak melampaui maksimum.
3. Temukan penyimpanan __minimum dan __maximum, lalu property untuk membacanya.
4. Buka allows untuk melihat bagaimana state satu object digunakan saat menguji satu harga.

### Contoh input dan hasil yang perlu dijelaskan

Buat dua object dengan maximum Decimal("10000") dan Decimal("20000"). Untuk harga Decimal("15000"), allows pada object pertama menghasilkan False dan pada object kedua True. Kode yang dipanggil sama, tetapi state yang dibaca berbeda. Menggunakan Decimal membantu membuat batas uang eksplisit.

### Hubungan dengan konsep OOP

Object nilai merangkum data dan keputusan yang konsisten. Constructor mencegah object terbentuk dalam keadaan rentang terbalik. Tidak ada self pelanggan global: referensi object budget diberikan atau disimpan oleh komponen yang membutuhkan batas tersebut.

### Batas penerapan dan kekeliruan yang perlu dihindari

Budget bukan dompet, pembayaran, atau total pesanan. Nilainya dipakai untuk penyaringan dan pemahaman kebutuhan. Persamaan budget melalui `__eq__` juga membandingkan nilai, bukan membuktikan kedua variabel menunjuk object yang sama.

### Latihan penelusuran

Mengapa dua budget berbeda bisa memakai allows yang sama? Prediksi hasil pada harga tepat sama dengan maximum saat maximum_inclusive=False.

## Kasus 3. Satu CartService mengikuti satu sesi yang diberikan

**Berkas utama:** [cart/services.py](../../cart/services.py#L25). **Simbol yang dibedah:** `CartService`.

### Masalah yang dihadapi

Dua browser memilih makanan berbeda. Constructor CartService menerima sesi, lalu membaca keranjang dari sesi itu. Karena dependency sesi diberikan saat object dibuat, layanan dapat bekerja pada sesi pelanggan yang sesuai tanpa menaruh semua keranjang dalam satu list kelas.

### Cuplikan kode nyata

Cuplikan `CartService.__init__` dari berkas sumber. Import dan bagian lain tidak ditampilkan.

```python
def __init__(self, session: SessionBase) -> None:
    self.session: SessionBase = session
    self._lines: list[CartLine] = deepcopy(session.get(self.SESSION_KEY, []))
```

### Bedah alur dan tanggung jawab

1. Baca SESSION_KEY: atribut kelas ini hanya menyatakan nama kunci "cart".
2. Telusuri `__init__`: self.session menyimpan referensi sesi, sedangkan self._lines mengambil deepcopy isi keranjang.
3. Baca _save untuk melihat kapan perubahan internal disalin kembali ke sesi.
4. Ikuti add_item dan clear; kedua method mengubah object penerima lalu menyimpan hasilnya.

### Contoh input dan hasil yang perlu dijelaskan

CartService(sesi_a) dan CartService(sesi_b) memakai nama kunci yang sama, tetapi isi sesi berbeda. Jika A mempunyai dua nasi dan B satu teh, clear pada layanan A mengosongkan keranjang A. Namun dua CartService yang diberi sesi yang sama bukan dua pelanggan: keduanya mengarah ke penyimpanan sesi yang sama.

### Hubungan dengan konsep OOP

Constructor menyambungkan perilaku layanan dengan dependency yang nyata. Instans tidak harus mewakili entitas database; CartService merupakan object layanan yang mengatur data sesi. self membedakan state internal setiap layanan, sementara sesi menentukan cakupan penyimpanannya.

### Batas penerapan dan kekeliruan yang perlu dihindari

Deepcopy bukan penguncian transaksi dan tidak menyelesaikan semua perubahan paralel. Data cart menyimpan ID/jumlah/pilihan, sedangkan harga dibaca lagi dari katalog server. Pembatas integer 1–99 berlaku pada tambah/gabung/edit yang relevan; update_quantity integer <= 0 tetap berarti hapus.

### Latihan penelusuran

Jelaskan perbedaan dua instans dengan dua sesi dan dua instans dengan satu sesi. Apakah SESSION_KEY harus berbeda untuk setiap pelanggan?

## Kasus 4. StaffAccess membawa pengguna yang sedang diperiksa

**Berkas utama:** [users/access.py](../../users/access.py#L18). **Simbol yang dibedah:** `StaffAccess`.

### Masalah yang dihadapi

Halaman operator perlu memutuskan apakah pengguna dapat mengelola katalog atau memakai kasir. StaffAccess menerima object pengguna, sehingga keputusan yang dibaca selalu berkaitan dengan pengguna yang diberikan pada instans tersebut.

### Cuplikan kode nyata

Cuplikan `StaffAccess.can_use_cashier` dari berkas sumber. Import dan bagian lain tidak ditampilkan.

```python
@property
def can_use_cashier(self) -> bool:
    return self._user.is_authenticated and (self._user.is_staff or self.is_cashier)
```

### Bedah alur dan tanggung jawab

1. Baca `__init__` dan atribut _user.
2. Periksa can_manage_catalog: autentikasi dan is_staff diperiksa bersama.
3. Periksa is_cashier: keputusan memakai keanggotaan grup bernama tepat Cashier.
4. Ikuti can_use_cashier serta home_route untuk membedakan izin akses dan pilihan tujuan navigasi.

### Contoh input dan hasil yang perlu dijelaskan

Untuk pengguna terautentikasi dengan is_staff=True, can_manage_catalog bernilai True. Untuk kasir biasa yang masuk grup Cashier tetapi bukan staf, can_use_cashier dapat True sedangkan can_manage_catalog False. Pengguna anonim tidak mendapatkan akses operator hanya karena halaman tombolnya terlihat.

### Hubungan dengan konsep OOP

Object ini membungkus kebijakan keputusan, bukan menyimpan akun baru. Menggunakan self._user membuat satu rancangan dapat dipakai untuk banyak pengguna. Property menyajikan hasil sebagai atribut baca, sehingga pemanggil tidak perlu mengulang ekspresi grup/staf di setiap tempat.

### Batas penerapan dan kekeliruan yang perlu dihindari

Membuat StaffAccess tidak melakukan login atau memberikan izin baru. Beberapa property dapat menjalankan query grup. Menyembunyikan tombol bukan pemeriksaan otorisasi yang cukup; view dan endpoint tetap harus menegakkan akses pada server.

### Latihan penelusuran

Bedakan object User dengan object StaffAccess. Mengapa keduanya tidak harus menjadi class induk dan turunan?

## Kasus 5. MenuSelection adalah object pilihan, bukan menu baru

**Berkas utama:** [menu/selection.py](../../menu/selection.py#L34). **Simbol yang dibedah:** `MenuSelection`.

### Masalah yang dihadapi

Dua pelanggan memilih menu katalog yang sama, tetapi varian dan tambahannya berbeda. Kita tidak perlu menggandakan MenuItem. MenuSelection mengemas referensi menu dan pilihan yang sedang dihitung menjadi satu object sementara.

### Cuplikan kode nyata

Cuplikan `MenuSelection.__init__` dari berkas sumber. Import dan bagian lain tidak ditampilkan.

```python
def __init__(
    self,
    item: MenuItem,
    options: Iterable[VariantOption] = (),
    addons: Iterable[AddOn] = (),
) -> None:
    self.item: MenuItem = item
    self.__options: tuple[VariantOption, ...] = tuple(options)
    self.__addons: tuple[AddOn, ...] = tuple(addons)
```

### Bedah alur dan tanggung jawab

1. Baca constructor yang menerima item, options, dan addons.
2. Perhatikan options/addons diubah menjadi tuple lalu disimpan pada instans.
3. Buka from_ids untuk melihat jalur pemilihan object katalog yang aktif dan sesuai menu.
4. Telusuri unit_price serta total_price untuk melihat perilaku perhitungan object pilihan.

### Contoh input dan hasil yang perlu dijelaskan

Sebagai ilustrasi, menu Rp18.000 dengan varian +Rp2.000 dan addon Rp3.000 menghasilkan unit_price Rp23.000. total_price(2) menghasilkan Rp46.000. Pilihan tanpa addon merupakan object pilihan lain yang dapat tetap menunjuk MenuItem yang sama.

### Hubungan dengan konsep OOP

Satu class tidak selalu sama dengan satu tabel. MenuSelection tidak mewarisi models.Model dan tidak mempunyai tabel sendiri. Ia membantu menyatukan data terkait dan perilaku harga saat dibutuhkan cart serta order. Instans ini hidup selama alur pemrosesan yang memakainya.

### Batas penerapan dan kekeliruan yang perlu dihindari

Constructor langsung hanya menampung object; from_ids melakukan validasi katalog. Pilihan sementara tidak menjamin katalog tidak akan berubah sebelum checkout. Server harus memeriksa pilihan kembali, dan harga contoh merupakan ilustrasi, bukan pembacaan database aktual.

### Latihan penelusuran

Gambar dua MenuSelection yang menunjuk satu MenuItem. Bagian mana yang sama dan bagian mana yang dapat berbeda?
