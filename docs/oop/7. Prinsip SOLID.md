# Modul 7. Prinsip SOLID

[Kembali ke indeks OOP](README.md). Diselaraskan dengan source project utama, 23 Oktober 2026.

SOLID membantu menjelaskan biaya perubahan desain. Jika aturan harga berubah, kita ingin menemukan tempat utamanya. Jika provider gagal, kita ingin caller tetap memahami hasilnya. Lima kasus berikut membahas satu prinsip per berkas utama, dengan bukti dan batasnya; ini bukan sertifikat bahwa seluruh proyek sudah memenuhi semua prinsip.

## Tujuan pembelajaran

- Menghubungkan setiap prinsip dengan kebutuhan perubahan konkret.
- Membedakan bukti kode, manfaat desain, dan keterbatasan yang masih ada.
- Menghindari klaim bahwa banyak class atau type hint otomatis berarti desain baik.

## Bekal istilah

| Istilah | Makna saat membaca kode |
|---|---|
| SRP | Satu kelompok tanggung jawab/alasan perubahan yang koheren. |
| OCP | Perluasan pada batas yang disediakan tanpa membongkar semua caller. |
| LSP | Implementasi pengganti memenuhi janji perilaku yang dibutuhkan caller. |
| ISP | Caller tidak dibebani kemampuan yang tidak diperlukannya. |
| DIP | Aturan tingkat tinggi memakai abstraksi dan dapat menerima alat dari luar. |

## Kasus 1. SRP: pilihan dan harga dipisahkan dari penyimpanan transaksi

**Berkas utama:** [menu/selection.py](../../menu/selection.py#L44). **Simbol yang dibedah:** `MenuSelection.from_ids`.

### Masalah yang dihadapi

Cart dan order sama-sama perlu memeriksa opsi yang dimiliki menu serta menghitung harga pilihan. Menaruh setiap aturan di view akan membuat perubahan varian harus dicari di banyak endpoint. MenuSelection memberi satu tempat yang berfokus pada pilihan katalog.

### Cuplikan kode nyata

Cuplikan `MenuSelection.from_ids` dari source saat penyelarasan; bagian berikutnya dilanjutkan di berkas sumber. Import dan bagian lain tidak ditampilkan.

```python
@classmethod
def from_ids(
    cls,
    item: MenuItem,
    variant_ids: Collection[int] = (),
    addon_ids: Collection[int] = (),
    *,
    invalid_variant: str = "Invalid variant selection.",
    incomplete_groups: str = "Select exactly one option for every required variant group.",
    invalid_addon: str = "Invalid add-on selection.",
) -> Self:
    """Resolve current catalog data while retaining caller-specific errors."""
    options = list(
        VariantOption.objects.select_related("group").filter(
            pk__in=variant_ids,
            is_active=True,
            group__menu_item=item,
            group__is_active=True,
```

### Bedah alur dan tanggung jawab

1. Baca from_ids untuk validasi opsi aktif, grup wajib, dan addon yang ditawarkan.
2. Baca unit_price untuk perhitungan berdasarkan pilihan.
3. Telusuri pemakai di cart/services.py dan orders/services.py.
4. Pisahkan tanggung jawab ini dari penyimpanan sesi, transaksi atomic, audit, dan respons HTTP.

### Contoh input dan hasil yang perlu dijelaskan

Jika aturan pilihan wajib berubah, pembaca mulai dari from_ids. Jika cara penyimpanan sesi berubah, pembaca mulai dari CartService. Jika checkout perlu mengurangi agregasi total, perubahan berada pada fungsi orders/services.py; tidak perlu menjadikan MenuSelection pengelola audit/pembayaran.

### Hubungan dengan konsep OOP

SRP berarti satu alasan perubahan utama yang koheren, bukan satu method per class. Validasi pilihan dan harga pilihan berkaitan pada domain selection. Model, layanan, dan view mempunyai tugas berbeda sehingga alur dapat dijelaskan per tanggung jawab.

### Batas penerapan dan kekeliruan yang perlu dihindari

Implementasi get_items masih menghitung harga tampilan sendiri dan validitasnya lebih sederhana; jangan mengklaim seluruh pengulangan sudah hilang. minimum_quote juga mempunyai logika katalog khusus. SRP digunakan untuk menilai batas, bukan membenarkan refactor luas tanpa kebutuhan.

### Latihan penelusuran

Tempatkan perubahan berikut pada komponen yang tepat: aturan varian wajib, format JSON, dan jumlah query SUM checkout.

## Kasus 2. OCP: implementasi generator dapat diperluas pada batas teks

**Berkas utama:** [recommendation/services/text_generator.py](../../recommendation/services/text_generator.py#L17). **Simbol yang dibedah:** `TextGenerator`.

### Masalah yang dihadapi

Tes penjelasan perlu jawaban deterministik tanpa API. Kontrak TextGenerator membuka kemungkinan memberikan implementasi lain, sehingga pemanggil generate yang sesuai kontrak tidak perlu berisi cabang khusus untuk setiap penyedia.

### Cuplikan kode nyata

Cuplikan `TextGenerator.generate_ranking` dari source saat penyelarasan. Import dan bagian lain tidak ditampilkan.

```python
def generate_ranking(self, prompt: str) -> str | None:
    """Optional ranking format support; text-only providers keep their behavior."""

    return self.generate(prompt)
```

### Bedah alur dan tanggung jawab

1. Baca method abstrak generate dan default generate_ranking.
2. Temukan constructor RecommendationExplanationService yang menerima TextGenerator.
3. Periksa pemanggilan self.gemini_client.generate(prompt).
4. Bandingkan dengan wrapper TurnGenerator yang juga memenuhi kontrak teks.

### Contoh input dan hasil yang perlu dijelaskan

Sebuah implementasi uji dapat mengembalikan teks JSON yang sudah ditentukan dari generate. Pemakai tetap menjalankan parsing/validasi hasil yang sama. Menambah implementasi generator tidak harus mengubah setiap pemanggilan generate yang sudah hanya bergantung pada antarmuka itu.

### Hubungan dengan konsep OOP

OCP terlihat pada titik perluasan, bukan janji tidak ada source yang boleh berubah selamanya. Abstraksi membantu membatasi area perubahan ketika alat pembuat teks diganti. Logika validasi domain tetap berada pada pemakai, bukan diserahkan bebas ke provider baru.

### Batas penerapan dan kekeliruan yang perlu dihindari

Tidak ada provider alternatif baru yang dipasang dalam pekerjaan dokumentasi ini. AI-first menggunakan available dan converse, sehingga perlu kontrak lebih luas untuk substitusi penuh. Memperluas generator teks saja tidak membuat chatbot otomatis kompatibel.

### Latihan penelusuran

Tentukan bagian caller yang tetap dan bagian implementasi baru yang perlu ditulis jika generator teks untuk tes diganti.

## Kasus 3. LSP: kegagalan adapter tetap mengikuti hasil str atau None

**Berkas utama:** [recommendation/services/gemini.py](../../recommendation/services/gemini.py#L61). **Simbol yang dibedah:** `GeminiClient._generate`.

### Masalah yang dihadapi

Provider dapat timeout, tidak dikonfigurasi, atau ditolak kuota. Caller yang dijanjikan str | None tidak boleh tiba-tiba menerima object respons SDK yang harus dipahami sendiri. Adapter menyederhanakan kondisi tersebut menjadi bentuk hasil yang dikenal.

### Cuplikan kode nyata

Cuplikan `GeminiClient.generate` dari source saat penyelarasan. Import dan bagian lain tidak ditampilkan.

```python
@override
def generate(self, prompt: str) -> str | None:
    return self._generate(prompt, structured_ranking=False)
```

### Bedah alur dan tanggung jawab

1. Bandingkan kontrak TextGenerator.generate dengan generate pada adapter.
2. Ikuti kondisi disabled, unconfigured, input_rejected, dan penolakan _allow_provider.
3. Periksa text dan batasnya setelah response SDK.
4. Baca penanganan exception yang mencatat metadata lalu mengembalikan None.

### Contoh input dan hasil yang perlu dijelaskan

Ketika kuota habis, hasil generate None dan last_event menerangkan quota_exhausted. Caller dapat memakai fallback sesuai kontraknya. Jika adapter malah mengembalikan dictionary {"error": ...} pada kondisi ini, caller yang mengharapkan string dapat rusak meskipun nama method sama.

### Hubungan dengan konsep OOP

LSP membahas penggantian dengan mempertahankan janji perilaku. Mengembalikan None bukan kegagalan desain ketika None memang bagian kontrak. Metadata terpisah memungkinkan diagnosis tanpa mencampur tipe hasil utama.

### Batas penerapan dan kekeliruan yang perlu dihindari

Type hint dan satu contoh hasil tidak membuktikan LSP di seluruh program. Konstruktor/configuration dan seluruh kebutuhan caller tetap perlu dipertimbangkan. Khusus GeminiAssistant, kontrak yang dibutuhkan lebih luas daripada TextGenerator.generate; jangan menyatakan semua turunan dapat dipasang di sana.

### Latihan penelusuran

Apakah mengembalikan None melanggar LSP? Apa perbedaannya dengan mengembalikan response SDK mentah?

## Kasus 4. ISP: pemakai keputusan akses tidak perlu menjadi pengelola akun

**Berkas utama:** [users/access.py](../../users/access.py#L18). **Simbol yang dibedah:** `StaffAccess`.

### Masalah yang dihadapi

Template atau view ingin menjawab pertanyaan akses, bukan membuat pengguna, mengubah password, atau mencatat pembayaran. StaffAccess memberikan antarmuka baca kecil yang relevan dengan keputusan operator.

### Cuplikan kode nyata

Cuplikan `StaffAccess.can_use_cashier` dari source saat penyelarasan. Import dan bagian lain tidak ditampilkan.

```python
@property
def can_use_cashier(self) -> bool:
    return self._user.is_authenticated and (self._user.is_staff or self.is_cashier)
```

### Bedah alur dan tanggung jawab

1. Daftar property can_manage_catalog, is_cashier, can_use_cashier, dan home_route.
2. Periksa dependency user pada constructor.
3. Bandingkan dengan model User dan layanan transaksi yang tidak digabung ke class ini.
4. Tunjukkan bagaimana caller cukup membaca property yang dibutuhkan.

### Contoh input dan hasil yang perlu dijelaskan

Halaman kasir dapat membaca can_use_cashier tanpa mengetahui alur pembuatan akun atau algoritma pembayaran. CMS dapat membaca can_manage_catalog. Keduanya memakai kebijakan yang sama tanpa harus bergantung pada object besar yang juga mengubah transaksi.

### Hubungan dengan konsep OOP

Ini ilustrasi antarmuka kecil yang sejalan dengan ISP: kemampuan yang tersedia sesuai kebutuhan kelompok caller. ISP tidak mengharuskan setiap property mempunyai ABC sendiri. Memisahkan kebijakan akses dari mutasi akun membuat ketergantungan lebih mudah dijelaskan.

### Batas penerapan dan kekeliruan yang perlu dihindari

StaffAccess bukan interface formal Python dan masih menerima object pengguna yang besar. Kasus ini menunjukkan arah desain, bukan pembuktian pemenuhan ISP seluruh aplikasi. Batas lain yang relevan adalah TextGenerator yang tidak memaksa semua generator memiliki converse; AI-first saat ini masih membutuhkan kontrak tambahan.

### Latihan penelusuran

Apa kerugian jika StaffAccess juga diwajibkan memproses refund dan mengubah password?

## Kasus 5. DIP: layanan penjelasan menerima dependency generator

**Berkas utama:** [recommendation/services/ai/explanations.py](../../recommendation/services/ai/explanations.py#L74). **Simbol yang dibedah:** `RecommendationExplanationService.__init__`.

### Masalah yang dihadapi

Aturan penjelasan perlu memeriksa fakta, format, dan klaim dari teks. Ia tidak seharusnya hanya dapat diuji dengan koneksi Google aktif. Parameter generator memungkinkan alat pembuat teks diberikan dari luar sementara aturan pemakainya tetap sama.

### Cuplikan kode nyata

Cuplikan `RecommendationExplanationService.__init__` dari source saat penyelarasan. Import dan bagian lain tidak ditampilkan.

```python
def __init__(self, gemini_client: TextGenerator | None = None) -> None:
    self.gemini_client: TextGenerator = (
        GeminiClient() if gemini_client is None else gemini_client
    )
    self.tag_extractor: TagExtractor = TagExtractor()
```

### Bedah alur dan tanggung jawab

1. Baca parameter gemini_client: TextGenerator | None.
2. Periksa pilihan memakai object parameter bila disediakan.
3. Temukan GeminiClient() sebagai fallback constructor ketika parameter None.
4. Ikuti _generate yang memanggil generator lalu memvalidasi JSON, ID, panjang, dan isi.

### Contoh input dan hasil yang perlu dijelaskan

Dengan dependency uji yang memenuhi generate, tes dapat memeriksa penolakan teks tak valid tanpa transport asli. Pada perangkaian ChatbotService, layanan penjelasan menerima TurnGenerator sehingga pembatas hybrid dibagi bersama komponen lain. Cara perangkaian alat dapat berubah tanpa membuang aturan validasi penjelasan.

### Hubungan dengan konsep OOP

Dependency injection adalah mekanisme memberi object dari luar. DIP merupakan arah ketergantungan ke abstraksi yang mendukung mekanisme tersebut. Kontrak TextGenerator membantu layanan berbicara dalam kemampuan yang dibutuhkan, bukan rincian SDK.

### Batas penerapan dan kekeliruan yang perlu dihindari

Penerapannya belum murni karena file masih mengimpor GeminiClient dan dapat membangunnya sebagai default. Ini perlu diakui dalam presentasi. Menerima dependency bukan alasan untuk percaya semua hasilnya; validasi pemakai tetap diperlukan dan AI-first masih mempunyai batas kontrak tersendiri.

### Latihan penelusuran

Bedakan dependency injection dan DIP. Bagian mana menunjukkan ketergantungan konkret yang masih tersisa?
