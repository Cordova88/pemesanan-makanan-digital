# 10. Latihan dan Presentasi

[Kembali ke indeks OOP](README.md). Diselaraskan pada 23 Oktober 2026.

Latihan ini melengkapi tujuh modul utama dengan lima kasus per modul. Mulai dari
source yang disebutkan. Bedakan prediksi hasil, hasil yang sudah dijalankan,
dan perilaku yang membutuhkan database/provider. Tidak perlu API nyata untuk
menjelaskan inheritance atau membuat ulang akun untuk mempelajari property.

## 1. Latihan class dan object

Buka menu/models.py, cart/services.py, dan users/access.py. Pilih satu class
model, satu layanan, dan satu object kebijakan. Untuk masing-masing, tuliskan
input constructor, dua state yang relevan, satu perilaku, dan apakah instansiasi
langsung menyimpan record database.

Tugas tambahan: gambar dua CartService yang menerima dua sesi berbeda, kemudian
dua CartService yang menerima satu sesi yang sama. Jelaskan kenapa jumlah instans
tidak selalu sama dengan jumlah pelanggan atau penyimpanan yang independen.

## 2. Latihan atribut dan method

Pada CartService, kelompokkan SESSION_KEY, session, _lines, _validate_quantity,
clear, dan total_for. Pada BudgetConstraint, kelompokkan from_dict, to_dict,
maximum, dan allows. Jelaskan dependency setiap operasi: hanya input, object
instans, atau class pembentuk object baru.

Jangan menjawab hanya dengan nama decorator. Untuk _validate_quantity, jelaskan
kenapa True ditolak. Untuk unit_price, jelaskan kenapa caller tidak menambahkan
tanda kurung. Untuk clear, jelaskan efek _save terhadap sesi.

## 3. Latihan enkapsulasi

Telusuri add_item ketika quantity awal 98 lalu ditambah 2. Tandai baris validasi
dan assignment. Prediksi apakah state lama berubah ketika ValidationError muncul.
Kemudian bandingkan perubahan dictionary hasil deepcopy dengan pemanggilan
update_quantity yang sah.

Buka MenuSelection dan jelaskan perbedaan mengubah list sumber sebelum/sesudah
constructor serta mengubah harga object AddOn di dalam tuple. Terakhir, tulis
daftar data yang hilang dan tetap setelah ConversationSession.reset.

## 4. Latihan relasi UML

Gambar Category–MenuItem, MenuItem–MenuTag, Order–OrderItem, dan
TurnGenerator–TextGenerator–provider. Setiap garis harus mempunyai bukti:
field model, deklarasi superclass, parameter constructor, atau pemanggilan method.
Tuliskan multiplisitas dan catatan PROTECT bila sesuai.

Uji diagrammu dengan pertanyaan: apakah garis ini menyatakan jenis, referensi,
atau penggunaan? Apakah ada bukti cascade delete? Apakah aturan order tidak kosong
merupakan constraint struktur semua keadaan atau aturan layanan create_order?

## 5. Latihan inheritance

Baca MenuPhotoForm.`__init__`, MenuPhotoWidget.get_context, MenuItem.save, serta
GeminiClient.generate. Buat tabel pekerjaan induk, pekerjaan anak, posisi super,
dan alasan super dipakai atau tidak dipakai.

Jelaskan perbedaan method abstrak yang harus diisi dan method framework yang
diperluas. Jangan menguji save pada data kerja untuk membuktikan inheritance;
prediksi dan penelusuran source cukup untuk latihan awal.

## 6. Latihan polimorfisme dan abstraksi

Bandingkan pemanggilan str pada model katalog, operator == pada budget, dan
generate pada provider/wrapper. Tulis siapa caller, siapa object penerima,
implementasi yang dipilih, dan kontrak hasilnya.

Tugas diagnosis: fake provider hanya mempunyai generate. Apakah ia dapat dipakai
oleh layanan penjelasan? Apakah ia memenuhi kebutuhan GeminiAssistant? Periksa
available dan converse di source sebelum memberi jawaban.

## 7. Latihan SOLID

Pilih satu prinsip dari modul 7. Sajikan kebutuhan perubahan yang masuk akal,
berkas utama yang akan dibaca, alasan desain saat ini membantu, dan keterbatasan
yang belum diselesaikan. Contoh untuk DIP: parameter generator tersedia tetapi
constructor layanan masih mempunyai default GeminiClient konkret.

Untuk SRP, jangan menjawab "satu class satu method". Untuk LSP, jangan menganggap
None otomatis salah karena kontrak mengizinkannya. Untuk ISP, jelaskan kebutuhan
caller daripada memecah semua property menjadi interface baru tanpa manfaat.

## 8. Latihan murni tanpa Django setup, database, atau API

Jalankan dari folder repository dengan interpreter proyek. Contoh berikut
menggunakan class proyek yang nyata. BudgetConstraint tidak mengimpor settings
Django atau membangun SDK client pada berkas ini.

```python
from decimal import Decimal
from recommendation.services.budget import BudgetConstraint

ketat = BudgetConstraint(maximum=Decimal("10000"))
longgar = BudgetConstraint(maximum=Decimal("20000"))
harga = Decimal("15000")
print(ketat.allows(harga))        # False
print(longgar.allows(harga))      # True
print(ketat == BudgetConstraint(maximum=Decimal("10000")))  # True
print(ketat is longgar)           # False

eksklusif = BudgetConstraint(maximum=Decimal("10000"), maximum_inclusive=False)
print(eksklusif.allows(Decimal("10000")))  # False
pulih = BudgetConstraint.from_dict(ketat.to_dict())
print(pulih == ketat)             # True
print(pulih is ketat)             # False

try:
    BudgetConstraint(minimum=Decimal("20000"), maximum=Decimal("10000"))
except ValueError:
    print("Rentang ditolak")
```

Prediksi keluaran sebelum menjalankan. Setelah itu jelaskan constructor,
property, method, persamaan nilai, identitas, serialisasi, dan invariant dengan
menunjuk class yang sama. Jangan mengganti latihan menjadi panggilan Gemini hanya
agar tampak lebih realistis.

## 10. Format catatan dan presentasi satu kasus

Gunakan urutan ini untuk penjelasan sekitar lima menit:

1. **Masalah:** satu kalimat tentang kebutuhan pengguna atau komponen.
2. **Bukti:** buka file dan simbol yang tepat; jangan hanya menampilkan diagram.
3. **State/input:** jelaskan asal data dan object penerima.
4. **Alur:** telusuri dua atau tiga langkah yang paling menentukan.
5. **Hasil:** beri satu contoh angka/teks yang dapat diperiksa dan satu kondisi gagal.
6. **Konsep:** kaitkan dengan satu konsep utama serta satu konsep pendukung.
7. **Batas:** jelaskan apa yang belum dijamin oleh mekanisme tersebut.

Contoh kerangka untuk cart: pelanggan sudah mempunyai 98 porsi; tambah dua
ditolak karena hasil gabungan 100. Tunjukkan validasi sebelum assignment,
penyimpanan _lines, dan defensive copy. Hubungkan dengan invariant dan
enkapsulasi, lalu sebutkan bahwa aturan ini bukan batas jumlah total baris.

## Rubrik review mandiri

| Unsur | Penjelasan kuat | Perlu diperbaiki |
|---|---|---|
| Bukti | Simbol dan source dapat ditunjukkan | Menyebut class fiktif atau nama yang salah |
| Penelusuran | Input–state–method–hasil jelas | Hanya membaca definisi teori |
| Konsep | Mekanisme dijelaskan dengan alasan | Menghitung underscore/keyword sebagai satu-satunya bukti |
| Batas | Konvensi dan jaminan runtime dibedakan | Menganggap tuple/ABC menjamin seluruh keamanan |
| Validasi | Prediksi dan hasil tes dibedakan | Mengaku lulus hanya karena ada test method |

Selesai latihan, minta teman memberi satu perubahan input dan telusuri ulang
tanpa menghafal naskah. Jika penjelasan runtuh saat nilai berubah, kembali ke
method yang menjaga aturan, bukan menambah definisi teori yang tidak terkait.
