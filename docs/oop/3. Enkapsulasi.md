# Modul 3. Enkapsulasi

[Kembali ke indeks OOP](README.md). Diselaraskan dengan source project utama, 23 Oktober 2026.

Pelanggan menambah satu porsi ketika keranjang sudah berisi 99. Object yang baik menolak perubahan itu sebelum state rusak. Enkapsulasi membahas jalur interaksi terhadap data dan invariant yang dijaga; penamaan private saja belum cukup. Modul ini membedah validasi, property, salinan, serta batas kepemilikan sesi.

## Tujuan pembelajaran

- Menjelaskan invariant dan jalur perubahan yang menjaganya.
- Membedakan underscore, name mangling, property, dan defensive copy.
- Menilai batas perlindungan object tanpa menyamakannya dengan otorisasi atau imutabilitas total.

## Bekal istilah

| Istilah | Makna saat membaca kode |
|---|---|
| Invariant | Aturan yang harus tetap benar sebelum dan sesudah operasi yang sah. |
| _nama | Konvensi internal, bukan larangan akses Python. |
| __nama | Name mangling membantu menghindari benturan nama; bukan penyimpanan rahasia. |
| Defensive copy | Salinan yang mencegah perubahan lewat referensi hasil langsung mengenai state internal. |

## Kasus 1. Budget menjaga rentang valid lewat constructor dan property

**Berkas utama:** [recommendation/services/budget.py](../../recommendation/services/budget.py#L17). **Simbol yang dibedah:** `BudgetConstraint`.

### Masalah yang dihadapi

Batas minimum yang lebih besar dari maksimum akan membuat penyaringan sulit dijelaskan. BudgetConstraint menolak keadaan tersebut saat inisialisasi dan tidak menyediakan setter publik untuk mengubah minimum/maximum setelah object terbentuk.

### Cuplikan kode nyata

Cuplikan `BudgetConstraint.__init__` dari berkas sumber; bagian berikutnya dilanjutkan di berkas sumber. Import dan bagian lain tidak ditampilkan.

```python
def __init__(
    self,
    minimum: Decimal | None = None,
    maximum: Decimal | None = None,
    *,
    minimum_inclusive: bool = True,
    maximum_inclusive: bool = True,
) -> None:
    for value in (minimum, maximum):
        if value is not None and (not value.is_finite() or value < 0 or value > 1_000_000):
            raise ValueError("Batas harga harus antara Rp0 dan Rp1.000.000.")

    if minimum is not None and maximum is not None and minimum > maximum:
        raise ValueError("Batas minimum tidak boleh melebihi maksimum.")

    self.__minimum: Decimal | None = minimum
    self.__maximum: Decimal | None = maximum
    self.__minimum_inclusive: bool = minimum_inclusive
```

### Bedah alur dan tanggung jawab

1. Baca validasi `__init__` sebelum penugasan atribut.
2. Temukan `__slots__` dan empat atribut dengan double underscore.
3. Periksa getter minimum, maximum, serta kedua flag inclusive.
4. Ikuti intersect yang membentuk BudgetConstraint baru sehingga hasil penggabungan tetap melewati validasi.

### Contoh input dan hasil yang perlu dijelaskan

BudgetConstraint(minimum=Decimal("20000"), maximum=Decimal("10000")) memunculkan ValueError. Untuk menaikkan batas maksimum, bentuk object baru melalui constructor atau rekonstruksi tervalidasi. Penugasan budget.maximum = ... tidak mempunyai setter publik yang disediakan class.

### Hubungan dengan konsep OOP

Enkapsulasi terlihat pada pembentukan state valid dan antarmuka baca yang terbatas. `__slots__` membatasi atribut instans biasa yang tersedia, sedangkan name mangling mengubah cara nama internal disimpan. Perlindungan utamanya tetap berupa kontrak dan validasi, bukan sulitnya mengeja atribut.

### Batas penerapan dan kekeliruan yang perlu dihindari

Python masih memungkinkan akses internal dengan nama yang telah di-mangle. Karena itu ini bukan pembatas terhadap penyerang yang mengendalikan proses. Jangan menyimpan key dalam __private lalu menganggap key tidak mungkin terbaca. Budget juga tidak mengunci saldo pengguna.

### Latihan penelusuran

Mengapa property tanpa setter belum cukup bila constructor menerima minimum > maximum?

## Kasus 2. Tuple melindungi struktur pilihan, bukan semua object di dalamnya

**Berkas utama:** [menu/selection.py](../../menu/selection.py#L97). **Simbol yang dibedah:** `MenuSelection`.

### Masalah yang dihadapi

Setelah opsi pelanggan ditentukan, pemanggil sebaiknya tidak menyisipkan addon baru melalui list yang sebelumnya diberikan. Constructor mengubah iterable menjadi tuple, lalu property mengembalikan tuple itu untuk pembacaan.

### Cuplikan kode nyata

Cuplikan `MenuSelection.addons` dari berkas sumber. Import dan bagian lain tidak ditampilkan.

```python
@property
def addons(self) -> tuple[AddOn, ...]:
    return self.__addons
```

### Bedah alur dan tanggung jawab

1. Baca tuple(options) dan tuple(addons) pada constructor.
2. Periksa getter options/addons yang tidak mempunyai setter.
3. Bandingkan dengan field item yang tetap referensi object model.
4. Ikuti from_ids untuk melihat validasi keanggotaan opsi dan addon sebelum selection dibuat.

### Contoh input dan hasil yang perlu dijelaskan

Jika daftar addons_awal berisi satu addon lalu dipakai membuat selection, append pada daftar asal tidak menambah anggota tuple selection. Namun jika harga object AddOn yang sama diubah di memori, unit_price dapat berubah ketika membaca referensi tersebut. Salinan struktur tidak sama dengan salinan mendalam seluruh graph object.

### Hubungan dengan konsep OOP

Class membatasi perubahan komposisi koleksi yang dipakainya. Pilihan property membedakan antarmuka baca dengan representasi internal. Di saat yang sama, ia sengaja tetap menggunakan referensi model katalog agar tidak menyamar sebagai snapshot transaksi.

### Batas penerapan dan kekeliruan yang perlu dihindari

Tuple bukan deep immutability. Constructor langsung juga tidak memeriksa katalog sebagaimana from_ids. Untuk data historis, order menyimpan snapshot harga/nama tersendiri; jangan menganggap selection yang masih menunjuk model hidup sebagai arsip harga.

### Latihan penelusuran

Prediksi efek append pada list sumber dan perubahan addon.price pada object yang sama. Mengapa hasil keduanya berbeda?

## Kasus 3. Keranjang memeriksa perubahan sebelum menyimpan dan menyalin hasil

**Berkas utama:** [cart/services.py](../../cart/services.py#L36). **Simbol yang dibedah:** `CartService.add_item`.

### Masalah yang dihadapi

Caller menerima dictionary baris setelah menambah menu. Jika dictionary itu adalah referensi internal, caller dapat mengganti quantity tanpa validasi. add_item mengembalikan deepcopy, sementara method perubahan publik tetap memeriksa input dan menyimpan hasil lewat _save.

### Cuplikan kode nyata

Cuplikan `CartService._save` dari berkas sumber. Import dan bagian lain tidak ditampilkan.

```python
def _save(self) -> None:
    self.session[self.SESSION_KEY] = deepcopy(self._lines)
    self.session.modified = True
```

### Bedah alur dan tanggung jawab

1. Baca _lines pada constructor dan _save yang memakai deepcopy.
2. Ikuti validasi note, quantity, ID, dan selection pada add_item.
3. Pada baris cocok, perhatikan combined_quantity diperiksa sebelum assignment.
4. Cari return deepcopy(line) dan bandingkan dengan checkout_items.

### Contoh input dan hasil yang perlu dijelaskan

Misalkan jumlah semula 98. Tambah satu berhasil menjadi 99; tambah satu lagi ditolak sebelum assignment. Mengubah hasil["quantity"] dari pemanggilan sukses tidak mengganti _lines. Baris dengan catatan berbeda tetap dapat menjadi baris terpisah, sebab kecocokan melibatkan konfigurasi dan catatan.

### Hubungan dengan konsep OOP

Enkapsulasi bukan sekadar memberi nama _lines. Ia mencakup pemilihan jalur mutasi, urutan validasi, dan pengendalian referensi mutable. Menghindari state setengah berubah membantu pemanggil menangani ValidationError tanpa perlu menebak apakah jumlah sudah tertimpa.

### Batas penerapan dan kekeliruan yang perlu dihindari

Batas 99 berlaku per baris pada jalur yang divalidasi, bukan batas total baris/session. Ini juga bukan penguncian konkurensi. Indikator valid pada get_items lebih sederhana daripada validasi checkout; checkout tetap perlu validasi otoritatif atas katalog.

### Latihan penelusuran

Apa perbedaan mengubah dictionary hasil add_item dan memanggil update_quantity? Mengapa penempatan validasi sebelum assignment penting?

## Kasus 4. Kebijakan akses disajikan sebagai hasil baca

**Berkas utama:** [users/access.py](../../users/access.py#L10). **Simbol yang dibedah:** `StaffAccess`.

### Masalah yang dihadapi

Template ingin tahu apakah tombol pengelolaan katalog perlu ditampilkan. Jika setiap template bebas menetapkan can_manage_catalog=True, logika akses akan tersebar. StaffAccess menyimpan pengguna dan menyediakan keputusan baca yang dihitung dari akun tersebut.

### Cuplikan kode nyata

Cuplikan `StaffAccess.can_manage_catalog` dari berkas sumber. Import dan bagian lain tidak ditampilkan.

```python
@property
def can_manage_catalog(self) -> bool:
    return self._user.is_authenticated and self._user.is_staff
```

### Bedah alur dan tanggung jawab

1. Baca _user sebagai referensi internal secara konvensi.
2. Ikuti can_manage_catalog dan can_use_cashier.
3. Perhatikan property tidak menyediakan setter untuk memberikan hak baru.
4. Bedakan home_route yang memilih tujuan dengan keputusan izin pada server.

### Contoh input dan hasil yang perlu dijelaskan

Kasir biasa dapat mengakses area kasir karena grup Cashier, tetapi tidak memperoleh akses katalog hanya dengan mempunyai object StaffAccess. Jika atribut user.is_staff berubah secara sah, hasil property pada object akses yang sama dapat ikut berubah karena ia membaca referensi pengguna, bukan membekukan snapshot peran.

### Hubungan dengan konsep OOP

Enkapsulasi membantu memusatkan ekspresi kebijakan. Pemanggil membaca pertanyaan domain seperti "boleh memakai kasir?" tanpa harus mengetahui semua detail grup. Tidak ada hubungan bahwa property sendiri merupakan middleware keamanan; ia hanya antarmuka keputusan yang dipakai komponen lain.

### Batas penerapan dan kekeliruan yang perlu dihindari

Satu underscore tidak menghalangi akses teknis ke _user. Pemeriksaan otorisasi tetap harus dilakukan pada request server dan tindakan transaksi. Logout POST + CSRF adalah kontrol HTTP terpisah; bukan konsekuensi otomatis dari penggunaan StaffAccess.

### Latihan penelusuran

Apakah can_manage_catalog tanpa setter sudah cukup melindungi endpoint? Jelaskan peran view dan class kebijakan.

## Kasus 5. Reset dialog hanya menghapus state yang dimiliki percakapan

**Berkas utama:** [recommendation/services/conversation_session.py](../../recommendation/services/conversation_session.py#L977). **Simbol yang dibedah:** `ConversationSession.reset`.

### Masalah yang dihadapi

Tombol Mulai Lagi perlu menghapus konteks percakapan lama, tetapi tidak boleh menghapus keranjang, login, atau counter penggunaan. ConversationSession membungkus sesi yang dimiliki Django dan mengubah subset kunci yang menjadi tanggung jawab dialog.

### Cuplikan kode nyata

Cuplikan `ConversationSession.reset` dari berkas sumber; bagian berikutnya dilanjutkan di berkas sumber. Import dan bagian lain tidak ditampilkan.

```python
def reset(self) -> None:
    for key in (
        self.STATE_KEY,
        self.SHOWN_KEY,
        "recommendation_context",
        self.TEMP_CONTEXT_KEY,
        "shown_recommendation_ids",
        "last_recommendations",
        "last_question",
        "recommendation_required_tags",
        self.SEARCH_KEY,
        self.LAST_RESULT_EMPTY_KEY,
        "recommendation_response_templates",
        "recommendation_last_message",
        "recommendation_last_response",
        self.ENTITY_KEY,
        self.REJECTED_KEY,
        self.INFERRED_KEY,
```

### Bedah alur dan tanggung jawab

1. Baca constructor: _session menerima sesi dari luar.
2. Ikuti daftar kunci pada reset, termasuk recommendation_last_message dan recommendation_last_response.
3. Perhatikan setiap kunci dihapus melalui pop(key, None), lalu modified ditandai True.
4. Bandingkan daftar tersebut dengan GEMINI_CALLS_KEY dan data cart/autentikasi yang sengaja tidak dihapus.

### Contoh input dan hasil yang perlu dijelaskan

Sebelum reset, sesi dapat berisi pesan lama, jawaban lama, gemini_calls=3, dan cart. Setelah reset, kedua teks lama tidak ada, tetapi counter tetap 3 dan cart tetap tersedia. Pada alur ChatbotService, reset dapat langsung diikuti sapaan AI baru sehingga nilai terkait percakapan baru bisa muncul kembali.

### Hubungan dengan konsep OOP

Ini contoh enkapsulasi berdasar kepemilikan state. Layanan memiliki kewenangan atas kunci dialog tertentu, bukan seluruh sesi. Reset menyatakan operasi domain yang jelas, sehingga pemanggil tidak perlu memanggil session.flush dan kehilangan data aplikasi lain.

### Batas penerapan dan kekeliruan yang perlu dihindari

Tidak semua method ConversationSession mengembalikan deep copy; load_state misalnya perlu dibaca sesuai implementasinya. Reset menghapus konteks lokal yang dipilih, bukan janji penghapusan riwayat pada layanan Google. Counter tidak direset agar tombol tidak menjadi jalan menghindari batas penggunaan.

### Latihan penelusuran

Mengapa session.clear/flush terlalu luas untuk tombol Mulai Lagi? Bedakan teks lama yang dihapus dengan sapaan baru setelah reset.
