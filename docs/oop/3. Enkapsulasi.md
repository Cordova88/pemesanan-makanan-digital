# Modul 3. Enkapsulasi

[Kembali ke indeks OOP](README.md). Mengikuti kode proyek utama pada 23 Oktober 2026.

Keranjang berisi 99 porsi. Ketika pelanggan menambah satu lagi, program harus menolak sebelum
jumlahnya berubah menjadi 100. Enkapsulasi membantu mengatur cara membaca dan mengubah data
supaya aturan seperti ini tetap dipenuhi. Pada modul ini, kita melihat pemeriksaan nilai,
salinan data, property, dan pembagian data yang boleh dihapus.

## Yang akan dipelajari

- Memahami masalah lewat contoh sebelum membaca kode.
- Menunjuk data dan method yang benar-benar dipakai pada lima berkas.
- Menjelaskan cara kerjanya dengan kata sendiri dan menyebutkan batasnya.

## Kasus 1. Batas harga diperiksa sebelum object dibuat

**Buka berkas:**
[recommendation/services/budget.py](../../recommendation/services/budget.py#L17). **Class atau
method yang dibahas:** `BudgetConstraint`.

### Masalah yang dihadapi

Batas minimum Rp20.000 dan maksimum Rp10.000 tidak masuk akal untuk satu pencarian.
`BudgetConstraint` memeriksanya sejak awal, sebelum data itu dipakai memilih menu.

### Cuplikan kode nyata

Ini bagian awal `BudgetConstraint.__init__`. Lanjutkan ke berkas aslinya untuk membaca seluruh
method. Bagian import tidak ditampilkan.

```python
def __init__(
    self,
    minimum: Decimal | None = None,
    maximum: Decimal | None = None,
    *,
    minimum_inclusive: bool = True,
    maximum_inclusive: bool = True,
) -> None:
    for value in (minimum, maximum):
        if value is not None and (not value.is_finite() or value < 0 or value > 1_000_000):
            raise ValueError("Batas harga harus antara Rp0 dan Rp1.000.000.")

    if minimum is not None and maximum is not None and minimum > maximum:
        raise ValueError("Batas minimum tidak boleh melebihi maksimum.")

    self.__minimum: Decimal | None = minimum
    self.__maximum: Decimal | None = maximum
    self.__minimum_inclusive: bool = minimum_inclusive
```

### Ikuti kode langkah demi langkah

1. Baca pemeriksaan pada `__init__` sebelum atribut diisi.
2. Temukan data minimum dan maksimum yang disimpan.
3. Baca property untuk melihat cara membaca batas tersebut.
4. Lihat `allows`: batas yang tersimpan dipakai untuk memeriksa harga tanpa mengubah object.

### Contoh masukan dan hasilnya

Minimum Rp20.000 dengan maksimum Rp10.000 memunculkan ValueError. Jika ingin batas baru, buat
BudgetConstraint baru dengan nilai yang benar. Property maximum tidak menyediakan cara mengubah
nilai lewat penugasan langsung seperti budget.maximum = ... .

### Mengapa ini contoh OOP?

Data tidak hanya dikumpulkan dalam satu class, tetapi juga dijaga melalui cara pembuatannya.
Property menyediakan cara membaca batas harga. Jika ingin batas berbeda, program membuat object
baru dengan pemeriksaan yang sama. Inilah bagian penting enkapsulasi: ada jalur yang jelas
untuk membuat data yang benar.

### Hal yang perlu diingat

Dua garis bawah bukan pengaman untuk menyimpan Kunci API. Python masih memungkinkan data
tersebut diakses dengan cara tertentu. Untuk contoh ini, yang menjaga batas harga adalah
pemeriksaan nilai dan cara penggunaan class, bukan nama atribut saja.

## Kasus 2. Daftar pilihan tetap, isi object di dalamnya masih bisa berubah

**Buka berkas:** [menu/selection.py](../../menu/selection.py#L97). **Class atau method yang
dibahas:** `MenuSelection`.

### Masalah yang dihadapi

Program sudah mencatat tambahan yang dipilih pelanggan. Jika daftar asal kemudian ditambah dari
bagian kode lain, pilihan yang sedang dihitung sebaiknya tidak ikut berubah tanpa sengaja.

### Cuplikan kode nyata

Potongan berikut berasal dari `MenuSelection.addons`. Bagian lain dapat dibaca pada berkas
aslinya.

```python
@property
def addons(self) -> tuple[AddOn, ...]:
    return self.__addons
```

### Ikuti kode langkah demi langkah

1. Lihat `tuple(options)` dan `tuple(addons)` pada awal pembuatan object.
2. Baca property options dan addons yang hanya mengembalikan pilihan.
3. Perhatikan item dan addon tetap menunjuk object katalog yang sama.
4. Bandingkan dengan `from_ids`, yang memeriksa apakah pilihan memang cocok untuk menu.

### Contoh masukan dan hasilnya

Jika list asal ditambah setelah selection dibuat, anggota tuple pada selection tidak ikut
bertambah. Tetapi jika harga addon yang sama diubah, perhitungan harga masih bisa berubah.
Mengunci daftar anggota berbeda dari membuat semua data anggotanya tidak bisa berubah.

### Mengapa ini contoh OOP?

`MenuSelection` mengubah daftar pilihan menjadi tuple. Tuple tidak menyediakan append untuk
menambah anggota. Dengan demikian, program membatasi cara mengubah daftar pilihan. Namun addon
di dalamnya masih object yang sama, sehingga ada perbedaan antara mengunci daftar anggota dan
mengunci seluruh isi masing-masing anggota.

### Hal yang perlu diingat

Jika harga object addon diubah, pembacaan harga pilihan masih bisa terpengaruh. Karena itu
tuple tidak boleh dijelaskan sebagai jaminan semua data di dalamnya tidak bisa berubah. Data
harga pesanan lama disimpan tersendiri ketika pesanan dibuat.

### Coba jelaskan kembali

Apa beda menambah anggota list asal dan mengubah harga addon yang sudah ada di dalam pilihan?

## Kasus 3. Keranjang memeriksa jumlah sebelum mengubah isinya

**Buka berkas:** [cart/services.py](../../cart/services.py#L36). **Class atau method yang
dibahas:** `CartService.add_item`.

### Masalah yang dihadapi

Setelah menambah makanan, bagian program lain menerima data baris keranjang. Jika data itu
langsung menunjuk baris asli, jumlah bisa diubah tanpa melewati pemeriksaan yang disediakan.

### Cuplikan kode nyata

Potongan berikut berasal dari `CartService._save`. Bagian lain dapat dibaca pada berkas
aslinya.

```python
def _save(self) -> None:
    self.session[self.SESSION_KEY] = deepcopy(self._lines)
    self.session.modified = True
```

### Ikuti kode langkah demi langkah

1. Lihat salinan isi sesi pada `_lines`.
2. Ikuti pemeriksaan jumlah dan pilihan pada `add_item`.
3. Temukan pemeriksaan combined_quantity sebelum quantity diganti.
4. Lihat `deepcopy` pada hasil dan `_save`, yang membuat salinan terpisah.

### Contoh masukan dan hasilnya

Jumlah 98 ditambah 1 berhasil menjadi 99. Penambahan 1 lagi ditolak, dan jumlah tetap 99. Jika
dictionary hasil penambahan diubah oleh pemanggil, perubahan itu tidak langsung mengenai baris
asli karena hasilnya sudah disalin.

### Mengapa ini contoh OOP?

CartService mengatur perubahan melalui method seperti `add_item` dan `update_quantity`. Saat
menggabungkan baris, jumlah baru diperiksa sebelum disimpan. Hasil yang diberikan ke pemanggil
juga berupa salinan. Jadi perlindungannya berasal dari urutan kerja dan pengelolaan data, bukan
hanya tanda garis bawah pada `_lines`.

### Hal yang perlu diingat

Batas 99 di sini berlaku per baris pada tindakan yang dijelaskan, bukan jumlah semua baris
dalam keranjang. Salinan juga tidak otomatis menyelesaikan dua permintaan yang datang
bersamaan. Pemeriksaan saat checkout tetap diperlukan.

### Coba jelaskan kembali

Mengapa memeriksa jumlah sebelum menyimpan lebih baik daripada menyimpannya dulu lalu
memeriksa?

## Kasus 4. Keputusan akses dibaca dari keadaan pengguna

**Buka berkas:** [users/access.py](../../users/access.py#L10). **Class atau method yang
dibahas:** `StaffAccess`.

### Masalah yang dihadapi

Halaman perlu mengetahui apakah pengguna boleh mengelola katalog. Jawabannya harus berasal dari
akun yang sedang diperiksa, bukan diisi sembarang oleh halaman.

### Cuplikan kode nyata

Potongan berikut berasal dari `StaffAccess.can_manage_catalog`. Bagian lain dapat dibaca pada
berkas aslinya.

```python
@property
def can_manage_catalog(self) -> bool:
    return self._user.is_authenticated and self._user.is_staff
```

### Ikuti kode langkah demi langkah

1. Temukan pengguna yang disimpan pada `_user`.
2. Baca `can_manage_catalog` dan `can_use_cashier`.
3. Perhatikan property menyediakan jawaban, bukan tombol untuk memberi izin baru.
4. Lihat penggunaan keputusan ini pada halaman atau tindakan server.

### Contoh masukan dan hasilnya

Kasir biasa tidak menjadi staf hanya karena dibuatkan object StaffAccess. Jika status staf
pengguna berubah secara sah, hasil pembacaan property dapat ikut berubah karena ia memakai
pengguna yang sama. Object pemeriksa tidak membekukan seluruh akun.

### Mengapa ini contoh OOP?

`StaffAccess` menyimpan pengguna dan menyediakan property untuk membaca keputusan. Bagian lain
cukup bertanya melalui property tersebut. Aturan mengenai staf dan grup kasir menjadi lebih
mudah ditemukan di satu tempat.

### Hal yang perlu diingat

Property tidak otomatis melindungi seluruh aplikasi. Bagian server yang menerima tindakan tetap
harus memakai pemeriksaan akses. `_user` juga hanya ditandai sebagai bagian dalam class; Python
tidak melarang seluruh akses kepadanya.

## Kasus 5. Mulai Lagi menghapus percakapan, bukan seluruh sesi

**Buka berkas:**
[recommendation/services/conversation_session.py](../../recommendation/services/conversation_session.py#L123).
**Class atau method yang dibahas:** `ConversationSession.reset`.

### Masalah yang dihadapi

Pelanggan menekan Mulai Lagi untuk mengulang percakapan. Ia tidak sedang meminta keranjang
dihapus, akun dikeluarkan, atau penghitung pemakaian Gemini dikosongkan.

### Cuplikan kode nyata

Ini bagian awal `ConversationSession.reset`. Lanjutkan ke berkas aslinya untuk membaca seluruh
method. Bagian import tidak ditampilkan.

```python
def reset(self) -> None:
    for key in (
        self.STATE_KEY,
        self.SHOWN_KEY,
        "recommendation_context",
        self.TEMP_CONTEXT_KEY,
        "shown_recommendation_ids",
        "last_recommendations",
        "last_question",
        "recommendation_required_tags",
        self.SEARCH_KEY,
        self.LAST_RESULT_EMPTY_KEY,
        "recommendation_response_templates",
        "recommendation_last_message",
        "recommendation_last_response",
        self.ENTITY_KEY,
        self.REJECTED_KEY,
        self.INFERRED_KEY,
```

### Ikuti kode langkah demi langkah

1. Lihat sesi yang diterima oleh ConversationSession.
2. Baca daftar nama data yang dihapus oleh `reset`.
3. Temukan pesan dan jawaban lama di daftar itu.
4. Periksa bahwa cart, login, dan penghitung Gemini tidak ikut dihapus.

### Contoh masukan dan hasilnya

Sebelum reset, sesi berisi pesan lama, jawaban lama, gemini_calls=3, dan cart. Setelah reset,
kedua teks lama hilang, tetapi penghitung tetap 3 dan cart tetap ada. Jika chatbot kemudian
meminta sapaan Gemini baru, teks percakapan baru bisa muncul lagi.

### Mengapa ini contoh OOP?

`ConversationSession.reset` menghapus daftar data yang memang menjadi bagian percakapan. Ini
membantu membatasi pekerjaan class: ia mengelola dialog, bukan seluruh data browser. Cara
menghapus yang jelas mencegah data lain ikut hilang karena memakai perintah terlalu luas.

### Hal yang perlu diingat

Reset menghapus teks dialog lama pada aplikasi. Jika Gemini aktif, aplikasi dapat meminta
sapaan baru sesudahnya sehingga data percakapan baru muncul lagi. Reset ini juga tidak berarti
data yang pernah diproses Google pasti dihapus dari sana.
