# Modul 6. Polimorfisme dan Abstraksi

[Kembali ke indeks OOP](README.md). Mengikuti kode proyek utama pada 23 Oktober 2026.

Kita dapat memanggil str pada menu dan grup varian, tetapi teks yang muncul berbeda. Kita juga
dapat memanggil generate pada dua pembuat teks yang cara kerjanya berbeda. Polimorfisme
membahas pemanggilan yang sama dengan pekerjaan yang disesuaikan object. Abstraksi membantu
memilih kemampuan apa yang perlu diketahui pemakainya.

## Yang akan dipelajari

- Memahami masalah lewat contoh sebelum membaca kode.
- Menunjuk data dan method yang benar-benar dipakai pada lima berkas.
- Menjelaskan cara kerjanya dengan kata sendiri dan menyebutkan batasnya.

## Arti istilah yang diperlukan

| Istilah | Penjelasan sederhana |
|---|---|
| Polimorfisme | Cara pemanggilan sama, tetapi pekerjaan yang dijalankan dapat berbeda sesuai object. |
| Abstraksi | Menunjukkan kemampuan yang dibutuhkan tanpa meminta pemakai memahami seluruh cara kerjanya. |
| ABC dan abstractmethod | Cara Python menandai class yang masih mewajibkan turunan mengisi method tertentu. |
| Method khusus Python | Method seperti __str__ dan __eq__ yang dipakai oleh operasi Python, misalnya str dan ==. |

## Kasus 1. TextGenerator menentukan kemampuan dasar yang harus ada

**Buka berkas:**
[recommendation/services/text_generator.py](../../recommendation/services/text_generator.py#L6).
**Class atau method yang dibahas:** `TextGenerator`.

### Masalah yang dihadapi

Layanan penjelasan ingin meminta teks. Ia perlu tahu cara meminta dan bentuk hasilnya, tetapi
tidak harus mengetahui cara menghubungi Google. TextGenerator menuliskan kemampuan dasar
tersebut.

### Cuplikan kode nyata

Potongan berikut berasal dari `TextGenerator`. Bagian lain dapat dibaca pada berkas aslinya.

```python
class TextGenerator(ABC):
    @abstractmethod
    def generate(self, prompt: str) -> str | None:
        """Return response text, or None when generation is unavailable/failed.

        Provider adapters handle their own provider/network failures. Consumers
        remain responsible for parsing and validating the returned text.
        """

        raise NotImplementedError

    def generate_ranking(self, prompt: str) -> str | None:
        """Optional ranking format support; text-only providers keep their behavior."""

        return self.generate(prompt)
```

### Ikuti kode langkah demi langkah

1. Baca TextGenerator yang ditandai sebagai ABC.
2. Lihat @abstractmethod pada generate.
3. Baca janji hasil: teks atau None.
4. Lihat generate_ranking bawaan yang meneruskan ke generate.

### Contoh masukan dan hasilnya

TextGenerator belum bisa dibuat sebagai object langsung karena generate belum diisi. Turunan
yang mengisi generate bisa dibuat object-nya. Jika turunan tidak mengubah generate_ranking,
versi bawaan memakai generate milik turunan itu.

### Mengapa ini contoh OOP?

Inilah contoh abstraksi: pemakai melihat method generate dan hasil teks atau None. Turunan
mengisi cara kerjanya. Saat method itu dipanggil pada object berbeda, Python menjalankan isi
method yang sesuai. Itulah hubungan abstraksi dan polimorfisme pada contoh ini.

### Hal yang perlu diingat

ABC membantu memastikan method wajib sudah diisi. ABC tidak menilai apakah seluruh kalimat AI
benar. Bagian yang memakai teks masih harus memeriksa isi dan formatnya. TextGenerator juga
belum menjanjikan kemampuan converse.

### Coba jelaskan kembali

Apa beda class yang belum bisa dibuat object dengan pembuat teks yang mengembalikan None?

## Kasus 2. Satu pemanggilan dapat diteruskan ke pembuat teks yang berbeda

**Buka berkas:**
[recommendation/services/ai/turn_generator.py](../../recommendation/services/ai/turn_generator.py#L69).
**Class atau method yang dibahas:** `TurnGenerator._generate`.

### Masalah yang dihadapi

TurnGenerator membatasi percobaan lalu meminta object pembuat teks mengerjakan sisanya. Pembuat
teks itu dapat memakai cara berbeda selama kemampuan yang dibutuhkan tersedia.

### Cuplikan kode nyata

Potongan berikut berasal dari `TurnGenerator._generate`. Bagian lain dapat dibaca pada berkas
aslinya.

```python
def _generate(self, prompt: str, *, ranking: bool) -> str | None:
    if self._private or not self._reserved or self._attempted:
        return None

    # Claim before dispatch; exceptions and invalid results cannot refund it.
    self._attempted = True

    try:
        if ranking and isinstance(self.provider, TextGenerator):
            return self.provider.generate_ranking(prompt)

        return self.provider.generate(prompt)
    except Exception:
        return None
```

### Ikuti kode langkah demi langkah

1. Bandingkan generate dengan generate_ranking.
2. Ikuti pemeriksaan pada _generate sebelum pekerjaan diteruskan.
3. Lihat kapan provider.generate_ranking dipakai.
4. Perhatikan hasil None ketika panggilan tidak boleh dilanjutkan atau layanan gagal.

### Contoh masukan dan hasilnya

Jika provider mempunyai generate_ranking khusus, method itu dipakai. Jika memakai bawaan
TextGenerator, pekerjaannya diteruskan ke generate. Pemakai tidak perlu mengubah cara memanggil
setiap kali cara pembuat teks berbeda.

### Mengapa ini contoh OOP?

Bagian pemanggil tidak perlu membuat percabangan untuk setiap nama layanan. Ia memanggil method
yang sama pada object yang diberikan. Jika object mempunyai generate_ranking khusus, cara itu
dipakai; jika tidak dan memakai bawaan TextGenerator, panggilan diteruskan ke generate.

### Hal yang perlu diingat

Object tiruan yang hanya punya generate belum tentu cukup untuk seluruh chatbot. Assistant
membutuhkan available dan converse. Selalu periksa kemampuan yang benar-benar dipakai, bukan
hanya kesamaan nama beberapa method.

### Coba jelaskan kembali

Jika provider hanya mengisi generate, bagaimana generate_ranking bawaan tetap dapat berjalan?

## Kasus 3. str menampilkan teks sesuai object yang diberikan

**Buka berkas:** [menu/models.py](../../menu/models.py#L142). **Class atau method yang
dibahas:** `VariantGroup.__str__`.

### Masalah yang dihadapi

Nama menu dan nama grup varian perlu tampil sebagai teks yang mudah dibaca. Pemakai cukup
memanggil str, lalu setiap model menentukan teks yang sesuai untuk dirinya.

### Cuplikan kode nyata

Potongan berikut berasal dari `VariantGroup.__str__`. Bagian lain dapat dibaca pada berkas
aslinya.

```python
def __str__(self) -> str:
    return f"{self.menu_item}: {self.name}"
```

### Ikuti kode langkah demi langkah

1. Baca __str__ pada MenuItem.
2. Bandingkan dengan __str__ pada MenuTag.
3. Baca __str__ pada VariantGroup yang menggabungkan nama menu dan grup.
4. Lihat bahwa str dipanggil dengan cara sama, tetapi isi method tiap model berbeda.

### Contoh masukan dan hasilnya

Untuk menu Nasi dan grup Ukuran, str(menu) dapat menghasilkan "Nasi", sedangkan str(grup)
menghasilkan "Nasi: Ukuran". Kode pemanggil cukup memakai str. Object yang diberikan menentukan
method mana yang dijalankan.

### Mengapa ini contoh OOP?

MenuItem mengembalikan nama menu. VariantGroup menggabungkan nama menu dan nama grup. Bentuk
pemanggilannya sama, tetapi method `__str__` yang dipilih berbeda. Contoh ini menunjukkan
polimorfisme tanpa harus membuat ABC baru untuk latihan.

### Hal yang perlu diingat

Teks hasil str bukan nomor pengenal yang pasti unik. Dua menu dapat mempunyai nama sama. Jangan
memakai label tampilan sebagai pengganti ID transaksi. Membaca hubungan untuk membentuk teks
juga dapat membutuhkan pembacaan database.

### Coba jelaskan kembali

Mengapa bagian pemanggil tidak harus memeriksa jenis object satu per satu sebelum memanggil
str?

## Kasus 4. Dua budget bisa bernilai sama meskipun object-nya berbeda

**Buka berkas:**
[recommendation/services/budget.py](../../recommendation/services/budget.py#L107). **Class atau
method yang dibahas:** `BudgetConstraint.__eq__`.

### Masalah yang dihadapi

Budget dapat dibuat ulang dari data sesi. Object yang baru tidak sama identitasnya dengan
object lama, tetapi isinya bisa sama. Program perlu cara membandingkan isi batas harga
tersebut.

### Cuplikan kode nyata

Potongan berikut berasal dari `BudgetConstraint.__eq__`. Bagian lain dapat dibaca pada berkas
aslinya.

```python
def __eq__(self, other: object) -> bool:
    return isinstance(other, BudgetConstraint) and (
        self.minimum,
        self.maximum,
        self.minimum_inclusive,
        self.maximum_inclusive,
    ) == (other.minimum, other.maximum, other.minimum_inclusive, other.maximum_inclusive)
```

### Ikuti kode langkah demi langkah

1. Baca __eq__ pada BudgetConstraint.
2. Lihat empat bagian nilai yang dibandingkan.
3. Bandingkan dengan __hash__ yang memakai nilai yang sama.
4. Bedakan == untuk isi dan is untuk object yang sama.

### Contoh masukan dan hasilnya

Dua budget berbeda yang sama-sama membatasi Rp10.000 dapat menghasilkan a == b bernilai True
dan a is b bernilai False. Jika satu budget menerima harga tepat Rp10.000 dan yang lain
menolaknya, isi aturan mereka tidak sama.

### Mengapa ini contoh OOP?

Method `__eq__` menentukan arti sama untuk BudgetConstraint. Ia membandingkan batas minimum,
maksimum, dan apakah angka tepat pada batas masih boleh diterima. Jadi operator == dapat
berarti membandingkan isi, sedangkan is memeriksa apakah dua nama menunjuk object yang sama.

### Hal yang perlu diingat

Sama nilainya tidak berarti milik pelanggan yang sama atau disimpan pada tempat yang sama. Saat
menjelaskan contoh, bedakan kesamaan isi dan kesamaan object. Pengaturan batas perlu ikut
dibandingkan karena dapat mengubah hasil pemeriksaan harga.

### Coba jelaskan kembali

Mengapa dua budget Rp10.000 dapat memenuhi a == b tetapi bukan a is b?

## Kasus 5. Form memakai cara kerja widget yang dipasang padanya

**Buka berkas:** [menu/widgets.py](../../menu/widgets.py#L12). **Class atau method yang
dibahas:** `MenuPhotoWidget.get_context`.

### Masalah yang dihadapi

Form dapat memakai widget input file bawaan atau widget foto khusus proyek. Keduanya mengikuti
cara penggunaan widget Django, tetapi yang khusus menambahkan informasi pratinjau.

### Cuplikan kode nyata

Potongan berikut berasal dari `MenuPhotoWidget.get_context`. Bagian lain dapat dibaca pada
berkas aslinya.

```python
def get_context(
    self,
    name: str,
    value: File | None,
    attrs: dict[str, object] | None,
) -> dict[str, object]:
    context = super().get_context(name, value, attrs)
    context["widget"]["photo_url"] = value.url if value and hasattr(value, "url") else ""

    return context
```

### Ikuti kode langkah demi langkah

1. Temukan get_context pada MenuPhotoWidget.
2. Lihat pemanggilan method induk melalui super.
3. Perhatikan tambahan photo_url.
4. Buka menu/forms.py untuk melihat field yang memakai widget ini.

### Contoh masukan dan hasilnya

Saat field memakai MenuPhotoWidget, data tampilannya mendapat tambahan alamat foto lama. Widget
file biasa tidak menambahkan bagian khusus itu. Form tetap memakai cara pemanggilan widget
Django yang sama.

### Mengapa ini contoh OOP?

Saat form menampilkan field, method get_context dari object widget yang dipasang akan
digunakan. Pemakai form tidak harus menulis ulang cara menampilkan setiap jenis widget. Object
widget-lah yang menentukan tambahan pekerjaannya.

### Hal yang perlu diingat

Hasil get_context tetap harus sesuai dengan kebutuhan Django dan template. Nama method yang
sama saja belum cukup jika bentuk hasilnya salah. Widget juga bukan pengganti pemeriksaan isi
gambar pada server.

### Coba jelaskan kembali

Apa yang berubah jika MenuPhotoWidget diganti dengan widget file bawaan Django?
