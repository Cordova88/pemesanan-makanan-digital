# Modul 5. Inheritance

[Kembali ke indeks OOP](README.md). Mengikuti kode proyek utama pada 23 Oktober 2026.

Form foto sudah mendapat banyak kemampuan dari Django. Proyek menambahkan bagian yang
dibutuhkan tanpa menulis ulang semuanya. Inheritance berarti membuat class turunan dari class
induk. Kita akan melihat bagian yang diwarisi, bagian yang diubah, dan alasan pemanggilan super
pada lima berkas nyata.

## Yang akan dipelajari

- Memahami masalah lewat contoh sebelum membaca kode.
- Menunjuk data dan method yang benar-benar dipakai pada lima berkas.
- Menjelaskan cara kerjanya dengan kata sendiri dan menyebutkan batasnya.

## Arti istilah yang diperlukan

| Istilah | Penjelasan sederhana |
|---|---|
| Class induk | Class asal yang menyediakan kemampuan untuk class lain. |
| Class turunan | Class yang mewarisi kemampuan induk dan dapat menambah atau menyesuaikannya. |
| Override | Menulis ulang method dari induk dengan pekerjaan yang sesuai kebutuhan turunan. |
| super() | Cara melanjutkan pemanggilan method menurut urutan pewarisan Python. |
| MRO | Nama urutan pencarian method pada class. Cukup pahami bahwa Python mempunyai urutan saat mencari method yang dipakai. |

## Kasus 1. GeminiClient mengisi kemampuan pembuat teks

**Buka berkas:**
[recommendation/services/gemini.py](../../recommendation/services/gemini.py#L61). **Class atau
method yang dibahas:** `GeminiClient.generate`.

### Masalah yang dihadapi

Bagian aplikasi yang membutuhkan teks ingin memanggil satu method yang jelas. Ia tidak perlu
ikut mengatur seluruh cara menghubungi Google. GeminiClient mengisi pekerjaan tersebut sebagai
turunan TextGenerator.

### Cuplikan kode nyata

Potongan berikut berasal dari `GeminiClient.generate`. Bagian lain dapat dibaca pada berkas
aslinya.

```python
@override
def generate(self, prompt: str) -> str | None:
    return self._generate(prompt)
```

### Ikuti kode langkah demi langkah

1. Temukan `GeminiClient(TextGenerator)`.
2. Bandingkan method generate pada class induk dan turunannya.
3. Ikuti generate ke _generate untuk melihat pemeriksaan dan panggilan Gemini.
4. Perhatikan converse adalah kemampuan tambahan yang tidak ditulis pada TextGenerator.

### Contoh masukan dan hasilnya

Generate dapat memberi teks atau None. Saat kuota habis, hasilnya None dan layanan tidak
dipanggil. Pada converse, satu pesan bisa membutuhkan beberapa putaran fungsi bantuan, tetapi
masing-masing tetap diperiksa kuotanya.

### Mengapa ini contoh OOP?

Class induk menetapkan kemampuan yang harus tersedia. Class turunan menentukan cara
menjalankannya. Pada kasus ini, `generate` milik GeminiClient memeriksa masukan, batas
penggunaan, lalu meminta teks ke Google. Nama method yang sama memberi cara pemanggilan yang
konsisten bagi pemakainya.

### Hal yang perlu diingat

Method generate induk belum berisi pekerjaan nyata dan akan menghasilkan NotImplementedError.
Karena itu turunan tidak perlu memanggil super().generate. Kemampuan converse merupakan
tambahan GeminiClient dan tidak otomatis dimiliki semua TextGenerator.

### Coba jelaskan kembali

Bagian mana yang merupakan janji class induk dan bagian mana yang khusus dikerjakan
GeminiClient?

## Kasus 2. BootstrapModelForm menyalurkan penataan tampilan ke seluruh form turunan

**Buka berkas:** [users/forms.py](../../users/forms.py#L11).
**Class atau method yang dibahas:** `BootstrapModelForm.__init__`.

### Masalah yang dihadapi

Panel CMS memiliki banyak form: kategori, tag, varian, dan meja. Jika setiap form harus mengatur
class styling Bootstrap (`form-control`, `form-select`, `form-check-input`) secara manual di setiap
field, kodenya akan berulang dan rawan terlewat.

### Cuplikan kode nyata

Potongan berikut berasal dari `BootstrapModelForm.__init__`. Bagian lain dapat dibaca pada berkas
aslinya.

```python
class BootstrapModelForm(forms.ModelForm):
    def __init__(self, *args: object, **kwargs: object) -> None:
        super().__init__(*args, **kwargs)

        for field in self.fields.values():
            if isinstance(field.widget, (forms.CheckboxInput, forms.CheckboxSelectMultiple)):
                field.widget.attrs["class"] = "form-check-input"
            elif isinstance(field.widget, forms.SelectMultiple):
                field.widget.attrs["class"] = "form-select"
            else:
                field.widget.attrs["class"] = "form-control"
```

### Ikuti kode langkah demi langkah

1. Temukan `class BootstrapModelForm(forms.ModelForm)`.
2. Lihat pemanggilan `super().__init__(*args, **kwargs)`. Django menyiapkan semua field form terlebih dahulu.
3. Perhatikan perulangan pada `self.fields.values()`. Form memeriksa jenis widget tiap field dan menyisipkan class Bootstrap yang sesuai.
4. Buka `CategoryForm` atau `MenuTagForm` di berkas yang sama untuk melihat bagaimana class turunan langsung mewarisi kemampuan penataan ini.

### Contoh masukan dan hasilnya

Saat `CategoryForm` dibuat, field nama otomatis memiliki attribute class `form-control`. Begitu pula saat
`MenuTagForm` dibuat. Tidak ada kode tambahan di dalam `CategoryForm` yang perlu mengatur styling Bootstrap
secara manual.

### Mengapa ini contoh OOP?

`BootstrapModelForm` mewarisi `forms.ModelForm` Django, memanfaatkan inisialisasi dasar milik induk via `super()`,
lalu memperkaya fungsionalitasnya. Class-class form lain cukup mewarisi `BootstrapModelForm` untuk mendapatkan
styling seragam. Ini prinsip *code reuse* yang elegan melalui inheritance.

### Hal yang perlu diingat

Pewarisan harus memanggil `super().__init__` agar field bawaan Django selesai dibuat sebelum diakses oleh
perulangan penataan atribut widget.

### Coba jelaskan kembali

Mengapa CategoryForm dan MenuTagForm tidak perlu mengatur class CSS form-control sendiri-sendiri?

## Kasus 3. MenuItem menambah pekerjaan sebelum penyimpanan Django

**Buka berkas:** [menu/models.py](../../menu/models.py#L71). **Class atau method yang
dibahas:** `MenuItem.save`.

### Masalah yang dihadapi

Foto menu perlu diperiksa dan diolah sebelum disimpan. Proyek memakai kemampuan penyimpanan
model dari Django, lalu menambahkan pekerjaan foto pada method save milik MenuItem.

### Cuplikan kode nyata

Potongan berikut berasal dari `MenuItem.save`. Bagian lain dapat dibaca pada berkas aslinya.

```python
def save(self, *args: object, **kwargs: object) -> None:
    update_fields = kwargs.get("update_fields")

    for field_name in ("image", "detail_image"):
        image = getattr(self, field_name)

        if (
            image
            and not image._committed
            and (update_fields is None or field_name in update_fields)
        ):
            from .image_processing import archive_original, prepare_photo

            photo = prepare_photo(image.file)
            archive_original(photo)
            setattr(self, field_name, photo)

    return super().save(*args, **kwargs)
```

### Ikuti kode langkah demi langkah

1. Lihat MenuItem yang mewarisi models.Model.
2. Baca pemeriksaan foto yang baru diunggah.
3. Temukan prepare_photo dan archive_original.
4. Lihat super().save yang meneruskan penyimpanan ke Django.

### Contoh masukan dan hasilnya

Jika ada foto baru yang termasuk field yang disimpan, foto diperiksa dan diolah terlebih
dahulu. Setelah itu penyimpanan model dilanjutkan. Jika penyimpanan hanya mengubah field lain,
kondisi pada kode membantu menghindari pengolahan foto yang tidak perlu.

### Mengapa ini contoh OOP?

Override tidak selalu berarti membuang seluruh kerja induk. MenuItem mengerjakan bagian khusus
foto, kemudian memanggil `super().save(...)` agar Django melanjutkan penyimpanan. Kita dapat
menunjuk dengan jelas mana kemampuan Django dan mana penambahan dari proyek.

### Hal yang perlu diingat

Penyimpanan foto benar-benar dapat menulis file dan data. Untuk belajar, cukup telusuri kode
dahulu. Beberapa cara menyimpan banyak data sekaligus juga tidak memanggil save setiap object
dengan cara yang sama; baca alurnya sebelum menyimpulkan.

### Coba jelaskan kembali

Apa akibatnya jika pekerjaan foto selesai tetapi penyimpanan induk tidak diteruskan?

## Kasus 4. Form menyiapkan data Django sebelum menambahkan kebutuhannya

**Buka berkas:** [menu/forms.py](../../menu/forms.py#L34). **Class atau method yang dibahas:**
`MenuPhotoForm.__init__`.

### Masalah yang dihadapi

Form foto membutuhkan nomor menu untuk membantu tampilan editor. Sebelum memakai field dan data
menu itu, Django harus menyiapkan form terlebih dahulu.

### Cuplikan kode nyata

Potongan berikut berasal dari `MenuPhotoForm.__init__`. Bagian lain dapat dibaca pada berkas
aslinya.

```python
def __init__(self, *args: object, **kwargs: object) -> None:
    super().__init__(*args, **kwargs)
    self.fields["image"].widget.attrs["data_menu_id"] = self.instance.pk or ""
    self.fields["detail_image"].widget.attrs["data_menu_id"] = self.instance.pk or ""
```

### Ikuti kode langkah demi langkah

1. Temukan MenuPhotoForm yang mewarisi ModelForm.
2. Lihat super().__init__ pada awal method.
3. Perhatikan self.fields dan self.instance baru dipakai sesudahnya.
4. Baca clean_image untuk membedakan penyiapan form dengan pemeriksaan foto.

### Contoh masukan dan hasilnya

Saat mengedit menu, data_menu_id berisi nomor menu yang sudah ada. Pada form baru, nomor itu
belum tersedia sehingga nilainya kosong. Menyiapkan form tidak langsung membuat menu baru di
database.

### Mengapa ini contoh OOP?

MenuPhotoForm memanggil `super().__init__` pada awal method. Sesudah itu, field dan instance
yang disediakan Django dapat dipakai untuk menambahkan atribut tampilan. Urutan ini penting:
pekerjaan turunan membutuhkan hasil penyiapan induk.

### Hal yang perlu diingat

Form baru belum mempunyai nomor menu yang tersimpan. Nilai kosong pada bagian itu adalah
keadaan yang wajar. Atribut HTML untuk editor juga bukan bukti bahwa pengguna berhak mengedit
menu; pemeriksaan server tetap terpisah.

### Coba jelaskan kembali

Mengapa super dipanggil sebelum kode membaca self.fields dan self.instance?

## Kasus 5. Widget foto menambahkan alamat gambar untuk pratinjau

**Buka berkas:** [menu/widgets.py](../../menu/widgets.py#L12). **Class atau method yang
dibahas:** `MenuPhotoWidget.get_context`.

### Masalah yang dihadapi

Input file bawaan Django sudah bisa menerima pilihan file. Proyek membutuhkan tambahan alamat
foto lama agar pengguna dapat melihat pratinjau. MenuPhotoWidget menambahkan informasi
tersebut.

### Cuplikan kode nyata

Potongan berikut berasal dari `MenuPhotoWidget.get_context`. Bagian lain dapat dibaca pada
berkas aslinya.

```python
def get_context(
    self,
    name: str,
    value: File | None,
    attrs: dict[str, object] | None,
) -> dict[str, object]:
    context = super().get_context(name, value, attrs)
    context["widget"]["photo_url"] = value.url if value and hasattr(value, "url") else ""

    return context
```

### Ikuti kode langkah demi langkah

1. Temukan MenuPhotoWidget yang mewarisi ClearableFileInput.
2. Lihat template dan file pendukung tampilan yang dipilih.
3. Baca super().get_context untuk mengambil data tampilan bawaan.
4. Lihat tambahan photo_url jika foto lama tersedia.

### Contoh masukan dan hasilnya

Jika foto sudah tersimpan dan mempunyai URL, photo_url berisi alamatnya. Jika belum ada foto,
nilainya kosong. Bagian tampilan bawaan Django tetap ikut karena hasil dari induk tidak
dibuang.

### Mengapa ini contoh OOP?

Method turunan mengambil data tampilan dari induk melalui super, lalu menambah `photo_url`.
Cara ini mempertahankan bagian bawaan yang masih dibutuhkan sambil menambahkan kemampuan
proyek. Membandingkannya dengan generate membantu kita melihat bahwa kebutuhan memanggil super
tergantung isi method induk.

### Hal yang perlu diingat

Pratinjau hanya membantu tampilan. File tetap harus diperiksa pada server, termasuk format,
ukuran, dan batas pikselnya. Gambar yang terlihat di browser belum berarti seluruh pemeriksaan
file sudah lulus.

### Coba jelaskan kembali

Mengapa membuat data tampilan dari nol dapat menghilangkan bagian yang sudah disediakan Django?

## Bagaimana Python mencari method?

Ketika object MenuPhotoWidget menerima panggilan method, Python mencari method yang sesuai
mulai dari class-nya dan mengikuti urutan pewarisan. Urutan ini disebut MRO. Kamu tidak perlu
menghafal seluruh rantainya untuk memahami contoh: lihat method mana yang ditulis pada class
proyek dan kapan super melanjutkan pekerjaan ke bagian berikutnya.

Pada GeminiClient.generate, method abstrak induk tidak diteruskan karena belum memberikan
pekerjaan nyata. Jadi kebutuhan memakai super ditentukan oleh cara kerja induknya, bukan aturan
bahwa semua method turunan wajib memanggil super.
